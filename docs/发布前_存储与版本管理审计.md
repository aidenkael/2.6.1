### 3.2 `calibration/` 根目录资源 vs 用户目录 `calibration_packages/`

**程序根目录 `calibration/`：**
- 属于**程序版本资源**，升级时整体替换
- `runtime_safety_baseline/calibration.json` 是空安全基线（无样本、无规则），声明"运行时使用确定性物理安全检查"
- `logistics_v2/packaging_rule_registry_v1.json` 是空规则注册表（`"aggregate_rules": [], "sample_rules": []`）
- `logistics_v2/logistics_config.json` 是物流公式参数（货代费率、汇率、体积除数等）

**用户目录 `calibration_packages/`：**
- 属于**用户数据目录**，升级时保留
- `builtin/` 子目录：由 `CalibrationManager.ensure_builtin()` 在首次启动时从程序根目录**复制**而来，注册到 SQLite
- `<timestamp>_*/` 子目录：用户手工导入的 Formal Bundle 或 legacy 校准包
- 运行时生效的是 `calibration_packages/` 中被 SQLite `calibration_packages` 表标记为 `active=1` 的包

**关系总结：**
程序根目录 `calibration/` 是**源模板**；用户目录 `calibration_packages/builtin/` 是**运行时副本**。启动时 `ensure_builtin()` 检查 SQLite 中是否已有同版本 builtin 注册，没有则从程序根目录复制并注册。

## 六、校准版本体系专项审计

### 6.1 当前 UI 显示

UI 中显示：

```
runtime-safety-baseline-v1
当前启用
2026-08-13...
```

### 6.2 各字段真实语义

**1. version 当前代表什么：**
- `CURRENT_BASELINE_VERSION = "runtime-safety-baseline-v1"`（`calibration_baseline.py` L16）
- 语义：内置安全基线的**版本标识符**，不是日期版本
- 当前只有一个版本：空安全基线（无样本、无规则）

**2. imported_at 当前代表什么：**
- SQLite `calibration_packages.imported_at` — 该包**首次注册到本地数据库的时间**
- 对 builtin：是首次启动时 `ensure_builtin()` 注册的时间
- **不是**算法版本更新时间

**3. builtin 首次登记时间是否会长期固定：**
- **是。** builtin 一旦注册到 SQLite，`imported_at` 固定不变
- `ensure_builtin()` 只在首次（无同版本 builtin 存在时）注册，后续启动发现已存在则跳过
- 即使软件更新内置基线内容，只要 version 不变，本地 `imported_at` 不更新

**4. Prompt 更新是否改变这里：**
- **不会。** Prompt 版本（`PROMPT_VERSION`）独立于校准版本
- Prompt 更新只影响 AI 识别结果，不改变校准包注册信息

**5. Packaging Engine 更新是否改变这里：**
- **不会。** Engine 版本（`ENGINE_VERSION`）独立于校准版本
- Engine 更新只影响包装估算逻辑，不改变校准包注册信息

**6. calibration resource 内容更新但 version 不变时会发生什么：**
- `ensure_builtin()` 检查 `version` 匹配 → 发现已有同版本 builtin → **跳过注册**
- 但会检查 `sample_count` 是否变化 → 如果变化则更新 metadata
- **不会重新复制文件**：已有 builtin 的 `path` 指向的文件不会被新版本覆盖
- **风险：** 如果新版本更新了 `calibration.json` 内容但保持 `version` 不变，用户本地的 builtin 副本**不会自动刷新**

**7. 已有用户本地 builtin 是否会自动刷新：**
- **不会。** `ensure_builtin()` 的幂等逻辑保证同版本只注册一次
- 文件只在 `path` 不存在时重写（`L284-289`）

**8. 是否存在"程序内置 calibration 已更新，但用户本地仍继续使用旧副本"的风险：**
- **当前不存在实际风险**：因为当前内置基线是**空安全基线**（无样本、无规则），内容极简且不太可能需要更新
- **但架构上存在风险**：如果未来更新了 builtin 内容但忘记递增 `CURRENT_BASELINE_VERSION`，用户本地不会刷新
- **缓解机制：** `purge_obsolete_bundled_calibration()` 在版本升级时会清理旧版本 builtin（按 `_LEGACY_BUNDLED_BASELINE_VERSIONS` 集合匹配），但当前只清理已知的旧 77 基线版本

### 6.3 结论

UI 显示的 `runtime-safety-baseline-v1` + `2026-08-13...` **不表示"仍在使用 8 月 13 日的旧算法"**。
- `runtime-safety-baseline-v1` 是**空安全基线的标识符**，不是算法版本
- `2026-08-13...` 是该基线**首次注册到本地数据库的时间**
- 当前真正的运行时行为由以下三者共同决定：
  1. **PackagingEstimationService**（ENGINE_VERSION = `packaging-estimation-v2-candidate-arbitration`）— 确定性物理安全仲裁
  2. **当前激活的校准包**（builtin 或 Formal Bundle）— 提供校准样本数据
  3. **logistics_v2 规则注册表** — 提供包装规则

## 九、数据库升级风险分析

### 9.1 当前 Schema 初始化方式

```sql
CREATE TABLE IF NOT EXISTS records (...)
CREATE TABLE IF NOT EXISTS snapshots (...)
CREATE TABLE IF NOT EXISTS settings (...)
CREATE TABLE IF NOT EXISTS calibration_packages (...)
-- ImageStore 追加：
CREATE TABLE IF NOT EXISTS images (...)
-- CalibrationFeedbackService 追加：
CREATE TABLE IF NOT EXISTS calibration_feedback (...)
```

**特征：**
- 全部使用 `CREATE TABLE IF NOT EXISTS` — 幂等创建，不破坏已有数据
- **无 `schema_version` 表** — 数据库本身不记录 schema 版本
- **无 migration 机制** — 没有 ALTER TABLE / 版本检测 / 迁移脚本
- **记录级 schema 版本** — `records.payload_json` 内有 `record_schema_version` 字段（`history-record-v2`），但这是记录数据语义版本，不是数据库表结构版本

### 9.2 未来加列/改表会发生什么

如果未来版本需要给某张表加列：
1. 当前代码只有 `CREATE TABLE IF NOT EXISTS` — **不会自动加列**
2. 旧数据库会保持旧 schema — 新代码引用新列时会报 `OperationalError: no such column`
3. **必须在加列的同时实现 migration 逻辑**

### 9.3 当前正式发布是否必须现在处理

**判断：可以等第一次真正修改 schema 时再实现。**

理由：
- 当前所有 6 张表的 schema 与代码完全匹配
- 没有"代码期望某列存在但数据库没有"的情况
- 在第一次需要 ALTER TABLE 时，引入 `schema_version` 表和 migration 框架即可
- 过早实现 migration 框架属于过度开发

**建议：** 在需要修改 schema 的那个版本，一次性实现：
1. SQLite 中增加 `schema_version` 表（单行，记录当前 schema 版本）
2. 启动时检查版本 → 按序执行 migration
3. 向后兼容：旧数据库自动升级，不丢失数据

## 十、未来三种更新场景的版本管理

### 场景 A：只修改软件功能（UI/业务逻辑）

| 更新项 | 是否更新 |
|---|---|
| 软件版本（pyproject + UI） | **是** |
| Prompt version | 否 |
| Engine version | 否 |
| Calibration version | 否 |
| 用户数据库 | 否（除非 schema 变更） |

### 场景 B：只修改 Prompt / Packaging Engine

| 更新项 | 是否更新 |
|---|---|
| 软件版本（pyproject + UI） | **是**（至少 bump patch） |
| Prompt version | **是**（改了就 bump） |
| Engine version | **是**（改了就 bump） |
| Calibration version | 否 |
| 用户数据库 | 否 |

### 场景 C：只修改正式校准规则

| 更新项 | 是否更新 |
|---|---|
| 软件版本（pyproject + UI） | 否（除非需要同步发布） |
| Prompt version | 否 |
| Engine version | 否 |
| Calibration version | **是**（Formal Bundle 自带版本） |
| 用户数据库 | 否（用户重新导入 Formal Bundle 即可） |

### 最简版本管理原则

1. **软件版本** = 用户感知的产品版本，任何用户可见变化都应 bump
2. **Prompt version** = AI 提示词变化时独立 bump，嵌入在代码常量中
3. **Engine version** = 包装估算算法变化时独立 bump，嵌入在代码常量中
4. **Calibration version** = 校准数据变化时由 Formal Bundle manifest 自带
5. **数据库 schema** = 表结构变化时才需要 migration，与软件版本解耦
6. **绝不混合**：Prompt 变了不代表 Engine 变了；Engine 变了不代表 Calibration 变了
